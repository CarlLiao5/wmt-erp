# Walmart 数据首次回填与持续增量同步设计

## 目标

为每个店铺建立可恢复、可追踪、幂等的 Walmart 数据同步流程：首次接入时按各接口允许的最大范围回填，后续按资源的更新语义持续增量同步。系统必须明确记录“接口允许的范围”和“本次实际覆盖的范围”，不能把没有接口支持的数据伪装成已完成。

## 已确认的 Walmart 接口边界

### 订单明细

`GET /v3/orders` 的官方限制必须在计划器中固化：

- 只能查询最近 180 天内创建的订单；180 天以前不能通过该明细接口获取。
- 单次查询条件的结果总数最多 10,000 条；超过会报错。
- 单页 `limit` 最大 200 条；200 是分页大小，不是总量上限。
- `createdStartDate`/`createdEndDate` 用于首次按日期窗口拆分；`lastModifiedStartDate`/`lastModifiedEndDate` 用于后续状态回补。

首次回填必须从当前时间向前 180 天开始，动态选择日期窗口；接口返回“超过 10,000 条”时将窗口二分，直到每个窗口可安全分页。不能通过单纯增加 offset 绕过 10,000 条总结果限制。

`GET /v3/orders/released` 同样只返回最近 180 天，不能作为历史明细替代品。订单绩效报表只返回参与对应指标的订单，不保证全量；Recon/Payment 返回结算交易，不能还原完整订单状态和商品明细。需要更早的完整订单时，支持人工导入 Walmart Seller Center 历史导出文件，导入来源和覆盖范围必须单独标记。

### 退货

`/v3/returns` 支持创建时间、最后修改时间和分页，但目录和文档没有确认统一的最大回溯天数。首次同步采用“边界探测”而不是硬编码天数：从较大的日期窗口开始，收到明确日期边界或连续窗口无数据时停止，并保存实际最早覆盖日期；接口拒绝时按窗口缩小重试。后续按 `lastModified` 重叠窗口同步，覆盖状态变化。

### Payment / Recon

Payment Statement 是当前账期快照，不接受通用的起止日期查询。Recon 先读取 `availableReconFiles` 返回的可用账期，再逐个账期下载；`reconFileJson` 每次最多 1,000 条，使用 `nextOffset` 分页到结束。首次回填范围由 Walmart 返回的可用账期决定，不以 180 天或本月替代。

### WFS 库存日志

WFS item inventory log 不传 `startDate` 时默认最近 90 天，直接查询最多最近 365 天；超过 365 天必须改用 `WFS_INVENTORY_LOG` 报告接口。直接接口默认 `limit=50`，按 `offset` 翻页。计划器必须传递日期窗口并记录使用的是直接接口还是报告接口。

### SEM、价格、广告和绩效

这些资源的历史可用范围由具体报告接口和店铺权限决定，当前不将未确认的天数写成硬限制。首次同步使用配置化窗口（SEM 默认 30 天，接口拒绝时缩小到 7 天），每个异步报告保存请求、轮询、下载和最终覆盖范围。价格、促销、广告和绩效只把接口实际返回的数据计入覆盖范围；空结果是“无数据/未授权”，不是零值。

## 统一同步模型

### 同步计划、窗口和任务

保留现有 `sync_jobs` 作为执行任务，并新增以下概念：

- **Sync Plan**：租户、店铺、资源、模式（`initial`/`incremental`）、目标起止范围、当前状态。
- **Sync Window**：计划拆出的一个 API 查询窗口，保存 `from`、`to`、请求参数摘要、估算/实际数量、分页游标、重试次数、覆盖状态和错误。
- **Sync Job**：一个窗口的一次执行尝试，沿用现有 BullMQ 和幂等键。
- **Coverage**：资源实际成功落库的最早、最晚时间，来源接口、报告账期或导入文件，以及是否完整。

窗口必须按 `tenant_id + store_id + resource + from + to + batch_id` 幂等。重试同一窗口只更新该窗口，不重复业务行；不同批次允许追加或修正。原始响应按页/报告文件独立写入 `raw_payloads`，不得覆盖。

### 首次接入流程

1. 创建店铺级资源计划，状态为 `planned`。
2. 根据资源策略生成窗口：订单从 180 天边界开始；退货边界探测；Recon 使用可用账期；库存日志按 365 天分段；报告类按配置窗口。
3. 将窗口加入队列，每个店铺独立限流，不能让一个店铺阻塞其他店铺。
4. 执行分页/异步报告，持久化原始响应、标准化业务表和窗口进度。
5. 只有所有必需窗口成功或明确标记为 `partial`，计划才结束；错误必须可重试。
6. Sync Status 展示每个资源的计划状态、实际覆盖范围、成功/失败窗口数和最近错误。

### 后续增量流程

- 订单：以 `lastModified` 为主，默认重叠 2 天；每天或按调度周期执行。
- 退货：以 `lastModified` 为主，默认重叠 7 天，覆盖状态和退款变化。
- Recon/Payment：轮询最新可用账期，已存在账期幂等重拉，允许账期补发。
- WFS 库存日志：同步最近 7/30 天窗口并定期重拉修正；库存快照按当前时点保存。
- SEM/广告/价格/绩效：按资源策略重叠窗口重拉，报告未完成时继续轮询，失败按 Retry-After 退避。

## 限流、重试和安全

- 统一读取 `Retry-After` 和 `x-next-replenishment-time`；429/5xx 指数退避，最大等待 120 秒。
- 不使用 Scan Form 的 100 次/分钟示例作为所有接口的额度。默认低并发、店铺独立令牌桶，实际响应头优先。
- 同一店铺的报告轮询、分页请求共享限流预算；超过预算进入延迟队列。
- Walmart 业务请求保持只读约束；报告接口若官方要求 POST，只允许固定的报告读取路径。
- 队列和日志不写入访问令牌、客户端密钥或原始认证头。

## 数据完整性与可观测性

- 每个窗口记录 API 参数摘要、响应页数、记录数、首尾业务日期、最后游标和完成时间。
- 重复游标立即失败当前窗口并保留已写入页，禁止死循环。
- “无数据”“未授权”“接口不支持历史”分别记录，不统一显示为成功零条。
- 订单 180 天以前的缺口要在 Sync Status 明确显示为接口边界；人工导入另记 `source=historical_import`。
- 所有聚合在租户和店铺权限过滤后执行。

## 验收标准

1. 订单首次计划覆盖当前日期向前 180 天；窗口超过 10,000 条时自动拆分；单页不超过 200 条。
2. 订单 180 天以前不会被标记为已同步；历史导入可单独显示来源和范围。
3. 退货首次同步能探测并记录实际最早日期，后续重叠窗口能更新状态。
4. Recon 能按可用账期完整分页，1,000 条边界和 `nextOffset` 正确处理。
5. WFS 日志 365 天内使用直接接口，超过范围切换报告策略或明确不可用。
6. 任意窗口失败可单独重试；重复执行不产生重复业务记录。
7. API、Worker、数据库和前端的权限、空数据、限流、恢复和完成时间均有测试与运行记录。
