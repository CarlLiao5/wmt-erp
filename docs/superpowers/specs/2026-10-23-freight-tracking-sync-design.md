# 货代物流轨迹同步 Work 设计

**状态：待用户审阅**
**日期：2026-10-23**

## 1. 目标

将 `/Users/carl/Downloads/new_system/` 中现有的多品牌物流追踪脚本接入 Walmart ERP，作为可从 Sync Status 手动触发、可查看任务状态与结果统计的同步 Work。货件来源是 ERP 已同步的头程在途数据，查询键为头程记录中的货代入库号。

本次只接入物流轨迹同步及其持久化，不新增物流业务页面，也不创建新的数据库实例。

## 2. 当前脚本行为

- 从头程在途数据读取去重后的货代入库号。
- 根据运单号前缀选择货代品牌：`QT → qitexp`、`TT → skytuo`、`DSL → desu`、`YLD/DP → depaex`。
- `qitexp`、`skytuo`、`depaex` 登录后按关键词搜索货件，再根据内部 ID 拉取详情；`desu` 从订单列表建立订单号到内部 ID 的映射，然后读取详情及轨迹。
- 分品牌并发执行，单品牌内部逐号处理；原脚本默认请求间隔为 0.5 秒。
- 已签收的货件跳过；最后事件超过 30 天没有更新的货件跳过；无品牌前缀映射的运单统计为未匹配。
- 每个可查询货件保存当前状态、最新事件时间、事件列表及详情原始响应。

## 3. 同步入口与处理流程

1. 管理员在 Sync Status 点击一个租户综合按钮「同步物流轨迹」。
2. API 验证管理员身份，并以会话中的 `tenant_id` 创建 `freight-tracking` 同步任务，写入现有 `sync_jobs`，加入 BullMQ。
3. Worker 按该租户从 `head_freight_rows` 读取非空 `freight_forwarder_inbound_number`，去重并保留来源头程记录关联。查询不依赖 store 是否匹配；货代号来自现有头程行。
4. Worker 按已确认前缀分组。未知前缀不调用外部接口，记入 `skippedUnmatched`。
5. Worker 对四个品牌并发执行，每个品牌内部顺序处理入库号，默认间隔 0.5 秒。每个货件独立捕获错误，单个货件失败不阻断其他货件。
6. Worker 根据已落库的最新轨迹应用过滤：状态为 `delivered` 的跳过；最新事件时间早于当前时间减 30 天的跳过。没有轨迹记录的货件首次执行时进入查询。
7. Worker 将抓取结果以事务方式写入 ERP 物流轨迹表，并保存原始响应。全批任务完成时状态为 `completed`，具体未找到/失败/跳过数放在结果统计中；只有头程读取、数据库连接等导致任务无法完成的任务级错误才标记为 `failed`。品牌配置缺失时该品牌的号码计为失败，其他品牌继续执行。

## 4. 凭证和安全边界

- Worker 运行时从当前 ERP MySQL 的 `WuLiulogin` 表按品牌读取 `username`、`password`、登录/查询地址及品牌扩展配置。
- 不复制凭证到 `.env`、前端、队列 payload、同步任务结果或原始响应表；密码和登录令牌不得出现在日志或异常信息中。
- `WuLiulogin` 仅作为凭证来源，不创建或迁移该表。读取字段须与当前真实表结构核对后实现；缺少品牌凭证应显示品牌名及配置缺失，不暴露凭证值。
- 仅允许 Worker 访问货代接口。API 和浏览器不直接访问货代服务。

## 5. ERP 数据模型

在现有 `walmart_erp` 数据库增加两张表：

### `freight_tracking_routes`

保存每个租户、货代入库号的最新状态，包括：主键、`tenant_id`、货代入库号、品牌、当前标准状态、状态原文、最新事件时间、最后抓取时间、最近成功同步批次、原始详情关联及创建/更新时间。

幂等唯一键为 `(tenant_id, freight_forwarder_inbound_number)`。相同货代号再次同步更新当前状态，不产生重复主记录。该表保留已签收和过期轨迹，供跳过规则判断。

### `freight_tracking_events`

保存该货代入库号返回的事件列表，包括事件时间、展示时间文本、描述、事件代码、顺序、原始事件 JSON、租户和路线关联。按 `(route_id, route_order)` 唯一；一次详情成功解析后，在同一事务内替换该货件的事件快照，防止旧轨迹残留或重抓重复。查询或解析失败不得清空旧事件。

### 原始数据

详情原始 JSON 写入现有 `raw_payloads`，资源标识为 `freight-tracking`，`store_id` 为空，`external_id` 使用稳定的租户和货代入库号标识并按现有 raw payload 约定留存；响应里不得有凭证或 token。状态/事件表与 `raw_payloads` 的关联 ID 按现有 schema 类型保存。

## 6. 任务结果和可观测性

Sync Status 最近任务列表增加资源名称「物流轨迹」。`result_payload` 返回以下脱敏计数：

- `sourceShipments`：头程表内去重后的非空入库号数
- `matched`：前缀可识别的入库号数
- `queried`：实际调用货代接口数
- `written`：成功保存详情/轨迹数
- `notFound`：接口未找到货件数
- `skippedDelivered`：已签收跳过数
- `skippedStale`：超过 30 天无更新跳过数
- `skippedUnmatched`：未识别品牌前缀数
- `failed`：查询或保存失败数

失败示例仅包含品牌、货代入库号及脱敏后的错误原因；不得包含请求头、密码、token、完整登录响应或包含凭证的 URL 参数。

- 全批处理完成后 Sync Job 状态为 `completed`，即使部分货件未找到或失败，也通过 `notFound` / `failed` 计数和错误摘要展示；只有任务级故障标为 `failed`。

## 7. 迁移和运行要求

- 新增标准 Drizzle schema、迁移 SQL、迁移 journal 项和针对解析/规则/存储/队列的测试。
- 遵循本仓库迁移人工审阅并手动应用的惯例；代码不会自动创建表或启动时执行迁移。
- API 对同步资源和租户范围作管理员验证；Worker 只查询当前租户头程行和同租户轨迹，不能跨租户去重或应用跳过规则。
- 任务日期窗口沿用通用 Sync Status 请求格式，但物流轨迹抓取集合始终由头程行决定，窗口不筛除货件。

## 8. 错误处理

- 某个入库号未找到：计入 `notFound`，继续。
- 某个入库号查询或解析失败：计入 `failed`，保留既有状态、事件与原始数据，继续处理其他入库号。
- 单品牌凭证缺失或认证失败：该品牌本批号码计入失败并标明品牌配置/认证错误，其他品牌继续。
- 头程表查询或数据库连接等任务级错误：任务失败并记录不含凭证的错误。
- 外部响应结构缺少轨迹列表：作为合法空轨迹还是解析失败，应在实现测试中按真实脚本返回结构验证；不得把解析失败解释成成功空数据并删除旧轨迹。
- `desu` 的旧脚本会使用用户主目录缓存订单号到内部 ID 的映射。Worker 不依赖单机文件缓存；映射仅在该次 Worker 任务内存中建立，避免多个部署进程读到过期或互不一致的本地缓存。

## 9. 验收标准

1. Sync Status 有且只有一个租户综合「同步物流轨迹」入口，普通成员不能触发。
2. 入库号来自 `head_freight_rows.freight_forwarder_inbound_number`，重复行只查询一次；未知前缀被统计且不发请求。
3. 四品牌映射正确，账号从 `WuLiulogin` 运行时读取；日志、BullMQ payload、任务响应和原始记录均不包含密码/token。
4. 已签收及 30 天无新事件的货件不会重复抓取；无既有轨迹的货件会首次查询。
5. 查询成功后最新状态、事件和原始响应都落在 `walmart_erp`；重复执行不会重复路线或事件；失败不会清掉旧数据。
6. 任务结果能区分抓取、未找到、跳过和失败数量；全批成功处理后状态为 `completed` 并保留局部失败计数，单货件/单品牌问题不会阻止其他品牌继续处理。
7. 迁移在空库和现有开发库结构检查通过；API、Worker、DB 类型检查与相关测试通过。
