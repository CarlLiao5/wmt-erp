# 订单、退货与 Payment 标准化入库切换规格

## 目标

以已导入的旧业务表作为历史完整性来源，恢复订单、订单商品行和退货的完整字段，并让持续同步直接写业务表。API 页面读取使用 MySQL 过滤、排序、分页和聚合，不再扫描 `raw_payloads`/JSON 后在 JavaScript 中重建订单与退货。原始响应仅作为审计和问题排查材料。

本次也将 Payment/Reconciliation 从“页面按需解析 `payment_reports.payload`”调整为报告归档加标准化交易行；具体字段从已接入的 Recon 交易字段中稳定映射，原始 JSON 仍可保留。

## 生产库盘点（只读）

生产库 `walmart` 中发现：

| 表 | 实际行数 | 当前用途/完整性 |
| --- | ---: | --- |
| `orders old` | 122,635 | 旧订单主记录，订单日期、客户订单号、地址区域、履约方式和状态齐全 |
| `order_items` | 134,839 | 旧订单商品行；SKU、数量、单价、币种、状态、运费、商品名、UPC、Item ID 齐全 |
| `returns` | 8,219 | 旧退货记录；数量、原因、退款、状态、日期及履约信息齐全，3 行没有 SKU |
| `orders` | 71,400 | 当前标准订单主表 |
| `order_lines` | 79,622 | 当前标准订单行表 |
| `return_records` | 3,149 | 当前标准退货表，字段少于旧 `returns` |
| `payment_reports` | 405 | 原始 Recon 页面归档 |
| `storage_fees` | 23 | 已标准化仓储费子集 |

旧订单商品行中发现 122,737 个不同店铺/PO 键；旧订单主表 122,635 个键。订单行键无重复。旧退货复合键无重复；3 行 SKU 缺失，不能静默丢弃。旧数据店铺名“鑫起典沃尔玛”映射到现有店铺“鑫启典沃尔玛”。其余旧表店铺名需与 `stores` 精确映射并在迁移前输出异常清单。

## 规范数据模型

- 订单主表保留旧订单主记录字段，包括 PO、customer order ID、客户邮箱（按当前管理员/成员字段可见性保护）、订单/预计送达时间、postal code、city、state、country、订单状态、金额/币种、履约方式、WFS 标记、来源及旧店铺名称；并补 `tenant_id`、`store_id`、更新时间和稳定唯一键。
- 订单商品行保留旧 `order_items` 的 line number、SKU、UPC、Item ID、商品名、数量、单价、币种、商品状态、shipping charge、时间字段；补 `tenant_id`、`store_id` 和订单主记录关联。SKU 元数据表可以继续服务商品目录，但不能成为历史订单明细的唯一载体。
- 退货表保留旧 `returns` 全部有业务意义的字段，包括 return/PO/customer order/return item IDs、SKU、商品名、数量、原因及原因码、退款金额、币种、退货/退款状态和日期、WFS/退货/配送方式；补 `tenant_id`、`store_id` 和索引。缺 SKU 的行保留并计入异常/可见数据，不影响其他退货。
- 新增标准 Recon 交易明细表，按租户、店铺、报告账期、交易/行标识、业务日期、描述、金额、币种和原始报告来源幂等保存；支持当前仓储费用与后续 Payment 页面需要的交易分类。交易行不可只保存成一段 JSON。
- `raw_payloads` 与 `payment_reports` 保留原始来源和审计能力；业务页面不解析它们来组装列表、趋势或分页数据。

## 路由与同步

- `/api/orders`、订单导出、订单详情、销量统计和商品分析订单查询，统一从标准订单主表与商品行表 SQL 查询。筛选、count、排序、page limit/offset、Pacific 日期界限和仪表盘所需聚合均由 SQL 完成。
- `/api/returns`、退货历史/趋势/原因分布与商品分析退货查询，从标准退货表 SQL 查询并聚合；如需状态历史，则单独标准化退货状态事件，不扫描 JSON 生成历史。
- Walmart 订单/退货 worker 的 API 响应先保留 raw archive，再将完整规范化字段在事务中 upsert 到标准业务表。重复窗口不得重复业务行；订单状态/退款状态更新要更新已有行。
- Recon worker 持久化原始报告页并逐行 upsert 到标准交易表；仓储费汇总从标准交易行派生，API 不得重新解析 Payment JSON。
- 删除或停用所有订单/退货 API 热路径中的 raw JSON 加载与 JavaScript 全量重建。

## 回填、切换与恢复

1. 生成只读 dry-run 报告：每个旧表按店铺的行数/日期范围、主子关联、重复键、空关键字段、无法映射店铺、标准表缺口及订单金额/数量汇总。
2. 为标准 schema 建兼容迁移，并将导入记录写入影子/暂存表；每批可重跑，记录 batch id 和来源 ID。
3. 先校验新旧数据的行数、店铺分布、日期范围、订单商品数量/金额、退货金额/数量及缺失项。明确列出 PO 主表缺失 102 个的关联处理结果，不能凭空补数据或静默跳过。
4. 对账达到验收条件后切换 API 读标准表，worker 切换到相同表写入；保留旧表和原始归档用于回滚。
5. 观察 API 查询响应时间和错误率，再单独决定是否清理旧表。未经单独确认不删除旧表、原始报告或 raw archive。

回滚方式是恢复旧查询实现/读源并停用新 worker 写入；迁移批次通过来源标记隔离，避免回滚时删掉并发新增数据。

## 安全与性能

- 每个业务查询都必须包含 tenant scope，并按成员店铺/SKU 权限裁剪；不能仅依赖 UI 过滤。
- 客户邮箱和地址字段沿用订单 API 现有字段脱敏策略；不扩大成员可见范围。
- 对订单日期/租户/店铺、订单行订单/SKU、退货日期/店铺/订单、Recon 日期/店铺/分类建立覆盖实际筛选的索引。
- 分页接口不得为计算一页结果而载入全量历史；列表响应行数受 `pageSize` 限制。
- 不记录认证信息和报告原始敏感字段到应用日志。

## 验收

- 历史数据：旧 `order_items` 134,839 行与新订单行逐店铺、逐日、逐 SKU 数量/金额对账；旧订单主键 122,635 行以及 102 个额外商品行 PO 均有可解释结果；退货 8,219 行（包括 3 行 SKU 缺失）均保留或有明确排除原因。
- 店铺映射包含“鑫起典沃尔玛”到店铺 ID `10002512034`（当前展示名“鑫启典沃尔玛”）。未知店铺数为零或有显式隔离记录。
- 增量重放同一订单/退货窗口两次，业务行不增加重复项，状态修改能更新。
- API 测试覆盖 tenant/store 权限、Pacific 日期界限、搜索/排序/分页、空状态历史和金额/数量聚合。
- 订单/退货页面热路径不查询 `raw_payloads`；Payment 业务查询不解析 `payment_reports.payload`。
- 使用代表性生产数据只读查询计划确认索引生效，并记录切换前后查询耗时；不以 JavaScript 返回正确为唯一通过标准。
- 全套相关 Worker/API/DB 测试和 typecheck 通过，`git diff --check` 通过；生产切换有可核验的批次统计和回滚点。
